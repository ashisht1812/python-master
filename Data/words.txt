I already have an ETM monitoring dashboard POC with HTML UI and mock data. Now I want to turn it into a production-style FastAPI app that:

Serves the UI and APIs from a single app / single Docker container

Uses FastAPI for APIs and Jinja2 + static files for the UI

Follows the MSIM pattern similar to msim_perfattr_alfalink (e.g. src/api/routes/positions.py)

Exposes APIs that can be used both by the dashboard JS and by other internal apps

Uses service functions in core modules as the single source of truth, with FastAPI routes as thin wrappers

Architecture & constraints

Use FastAPI, not Flask.

Single app, single port, suitable for one Docker container:

/ and maybe /jobs, /accounts etc. → HTML UI

/static/... → JS/CSS/assets

/api/v1/... → JSON APIs

The exact names can be adjusted, but keep api/routes for FastAPI routers and core for business logic.

Follow the same style as msim_perfattr_alfalink:

src/api/main.py (or similar) to build the FastAPI app and register routers

src/api/routes/*.py with APIRouter, Depends, Annotated, Query, etc.

Import extractors/services from core/* instead of putting logic in routes

Business logic (monitoring, retries, job orchestration) must live in core services, not in routes:

Example: core.jobs.service.start_batch_job(req) is the real implementation

API route just parses request → calls service → returns result

Internal Python code (scheduler, batch worker) should call the same services directly, without going through HTTP

API design requirements

Design the API so that:

Everything is versioned under /api/v1/...

Responses are pure JSON, no HTML fragments

The same API can be safely called by:

Browser JS (dashboard)

Other internal apps / services

I need concrete endpoints for:

Overview & monitoring

GET /api/v1/overview?date=YYYY-MM-DD

GET /api/v1/processing-timeline?days=7

GET /api/v1/status-by-team?date=...

GET /api/v1/system/status

Failed accounts & actions

GET /api/v1/accounts/failed?date=...

POST /api/v1/accounts/retry-failed?date=...

POST /api/v1/accounts/process-pending?date=...

POST /api/v1/accounts/{account_id}/retry

Jobs & history

GET /api/v1/jobs/active

GET /api/v1/jobs/history?date=...&limit=20

GET /api/v1/jobs/{job_id}

POST /api/v1/jobs/start

POST /api/v1/jobs/{job_id}/cancel

Portfolios / scheduling

GET /api/v1/portfolios?date=...

For each endpoint, use Pydantic models for request/response where appropriate and keep the shapes UI-agnostic.

UI behaviour

The HTML dashboard (Jinja2 templates in ui/templates) should load once.

A ui/static/js/dashboard.js file should:

Call the above /api/v1/... endpoints via fetch

Refresh overview tiles, charts, system status, active jobs, failed accounts, etc.

Use polling (e.g. every 10 seconds) for updates; do not add WebSockets for now.
